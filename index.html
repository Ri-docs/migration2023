RapidIdentity 2023 On-Prem Migration

Scope

Use this guide for older on-prem appliance replacement work where new DB, ARMS/Portal, and DSS/Connect appliances are built on the same RapidIdentity version as the source environment before migration.

This flow is intended for migrations from older RapidIdentity appliances, such as 2019-era environments, to a replacement appliance set that can then be upgraded after validation.

The guide is split into two parts: customer preparation before the scheduled migration call, followed by support-led migration steps performed during the call.

Customer prep before the migration call

Stop after the hosts file step unless Identity Automation Support instructs you to continue. Do not power down the legacy appliances and do not reuse production IP addresses during prep.

Create one new appliance for each current legacy appliance role. A typical environment has one DB appliance, one ARMS/Portal appliance, and one DSS/Connect appliance.

  • Use the same hypervisor platform that currently hosts the legacy appliances. For Hyper-V, choose Generation 1.
  • Match the memory and disk size of the corresponding legacy appliance. Do not enable Dynamic Memory.
  • Connect each new VM to the same network or subnet as the legacy appliances.
  • Use temporary IP addresses for the new appliances. Production IP cutover happens later.
  • Install the same RapidIdentity 2019 LTS release currently running on the legacy appliances.
  • Use the appliance ISO attached to the support case. If the attachment is unavailable, use the RapidIdentity latest ISO link provided by Support.

Build each replacement VM

  1. Name each VM clearly for its role, such as DB, ARMS, or DSS.
  2. Assign static memory that matches the current appliance.
  3. Create a virtual hard drive that matches the current appliance disk size.
  4. Attach the VM to the same virtual network used by the existing appliance.
  5. For Hyper-V, select the option to install an operating system later, then attach the ISO after the VM is created.

Install the appliance OS and RapidIdentity

  1. Boot the new VM from the RapidIdentity appliance ISO.
  2. If the VM does not boot from the installer, confirm the ISO is attached and the VM is booting from the virtual DVD device.
  3. When the installer appears, choose the latest 2019 LTS release.
  4. Let the installation complete without interruption.
  5. Set the password for the automatically created config user and record it for the migration call.
  6. After the first reboot, remove the installation media and reboot again so the VM starts from the installed appliance OS.
  7. Sign in as config and configure temporary static network settings.
  8. Install RapidIdentity from the appliance menu, let the install finish, and reboot when prompted.
  9. Confirm the appliance login screen shows the configured temporary IP address. If it does not refresh immediately, sign in as config and sign back out.

Temporary network settings

Use manual IPv4 configuration with a temporary IP address on the same subnet as the legacy appliances. Enter the correct gateway, DNS servers, and search domains for the customer's network.

Menu path after installation:

System > Network > Network Settings > Basic Network Settings > Edit a connection

Set the idautodb hosts entry

After RapidIdentity is installed and networking is configured, sign in as config and open the hosts file menu.

System > Network > Network Settings > Hosts File
Appliance Hosts entry Notes
DB appliance localhost idautodb Use this only on the new DB appliance.
Non-DB appliances <temporary-db-ip> idautodb Use the temporary IP address assigned to the new DB appliance.
Stop here for customer prep. Do not attempt PostgreSQL installation, repository repair, migration scripts, service shutdown, or IP cutover before the scheduled migration call.

Ready for the migration call

Before the call, confirm these items are complete and provide the temporary IP address for each new appliance role.

  • One new appliance exists for each current legacy appliance role.
  • If using Hyper-V, each VM is Generation 1.
  • Dynamic Memory is disabled.
  • Memory and disk sizing match the current appliances.
  • Each new appliance is connected to the same network or subnet as the legacy appliances.
  • Each new appliance has a temporary IP address, and no production legacy IP has been reused.
  • The config password is recorded for the migration call.
  • RapidIdentity 2019 LTS is installed on each new appliance.
  • The hosts file includes the correct idautodb entry on each appliance.
  • The new appliances can communicate with each other on the network.
New DB: <temporary IP>
New DSS/Connect: <temporary IP>
New ARMS/Portal: <temporary IP>

Support call starting point

Begin here during the scheduled migration call after customer preparation is complete.
  1. Confirm the appliance role and temporary IP map.
  2. Confirm idautodb resolves correctly on each target appliance.
  3. Snapshot the source appliances before making changes.
  4. Confirm a recent PostgreSQL backup exists on the source DB appliance.
psql idautodb idautoAdmin -t -A -c "show server_version; show server_version_num;"
ls -lh /var/opt/idauto/backup/idautodb_pg_backup_*.sql.gz | tail

Repair yum repositories on the target DB appliance

Run this before installing or configuring PostgreSQL on older CentOS 7 based appliances. Stale MySQL and version-specific PGDG repositories can block appliance setup and RapidIdentity updates.
  1. Download and run the repo cleanup script.
cd /var/tmp
curl -fsSLO https://ri-docs-files.s3.us-east-1.amazonaws.com/ri-repo-fix.zip
unzip -o ri-repo-fix.zip -d /var/tmp/ri-repo-fix
chmod +x /var/tmp/ri-repo-fix/ri-repo-fix.sh
bash /var/tmp/ri-repo-fix/ri-repo-fix.sh
  1. If the PostgreSQL install fails with No package postgresql11-server available, add the PostgreSQL 11 archive repository.
cat > /etc/yum.repos.d/pgdg-11-archive.repo <<'EOF'
[pgdg11-archive]
name=PostgreSQL 11 archive for RHEL/CentOS 7 - x86_64
baseurl=https://yum-archive.postgresql.org/11/redhat/rhel-7-x86_64
enabled=1
gpgcheck=1
gpgkey=file:///etc/pki/rpm-gpg/PGDG-RPM-GPG-KEY-RHEL7
EOF

yum clean all
yum makecache
yum list available postgresql11-server postgresql11-contrib
  1. Return to the appliance PostgreSQL setup or database role installation step and retry it.

Download the migration bundle

Run this on each target appliance.

cd /root
rm -rf migrate-appliance migrate-appliance.tar.gz
curl -fL -o migrate-appliance.tar.gz https://idauto-apps.s3.amazonaws.com/appliance-migrate/migrate-appliance.tar.gz
tar -xzf migrate-appliance.tar.gz
chmod 700 migrate-appliance.sh

Source appliance shutdown

Stop RapidIdentity on the source appliances during the maintenance window before running migration.

Stop services on the source ARMS/Portal, DSS/Connect, and DB appliances.

service rapididentity stop

Target DB appliance migration

  1. Confirm idautodb resolves locally on the target DB appliance.
  2. Run the migration script against the source DB appliance.
./migrate-appliance.sh --src-host=<source-db-ip> --target-db-host=localhost --migrate-db

Review the script output before moving to the non-DB appliances.

Target ARMS/Portal appliance migration

  1. Confirm idautodb resolves to the target DB appliance.
  2. Run the migration script against the source ARMS/Portal appliance.
./migrate-appliance.sh --src-host=<source-arms-ip> --target-db-host=idautodb --migrate-db

Target DSS/Connect appliance migration

  1. Confirm idautodb resolves to the target DB appliance.
  2. Run the migration script against the source DSS/Connect appliance.
./migrate-appliance.sh --src-host=<source-dss-ip> --target-db-host=idautodb --migrate-db

Validate before cutover

  1. Start RapidIdentity on the target DB, DSS/Connect, and ARMS/Portal appliances.
  2. Confirm Portal and Configuration load successfully.
  3. Confirm Connect loads and the Jobs page is available.
  4. Confirm the target appliances appear healthy in the cluster view.
  5. Validate database-backed configuration such as SAML, LDAP, licenses, applications, workflows, and representative jobs.
  6. Review logs on each node before transferring production IPs.
service rapididentity start

If configuration data is missing

If the script migration completes but SAML, LDAP, license, application, or workflow configuration is missing, restore from a known-good PostgreSQL dump instead of relying on UI database migration.
  1. Copy the current source DB backup to the target DB appliance.
  2. Stop RapidIdentity on every target appliance connected to the target DB.
  3. Restore the dump into idautodb and capture a restore log.
gunzip -c /path/to/idautodb_pg_backup.sql.gz | psql idautodb idautoAdmin 2>&1 | tee /tmp/idautodb_restore.log
  1. Validate the expected configuration tables contain data.
  2. Start RapidIdentity again and repeat validation.
psql idautodb idautoAdmin -c "select count(*) from saml_idp;"
service rapididentity start

Restore logs may include early does not exist messages when the dump contains clean/drop statements. Treat those as noise only after confirming the restore completes and expected tables contain data.

Cutover

  1. Snapshot the new target appliances after validation passes.
  2. If supported by the hypervisor, disconnect or disable the old appliance NICs before moving production IPs.
  3. Shut down old appliances in this order: ARMS/Portal, DSS/Connect, DB.
  4. Move the production IPs to the new appliances.
  5. Update each target appliance hosts file so idautodb maps to the production DB IP.
  6. Start new appliances in this order: DB, DSS/Connect, ARMS/Portal.
  7. Validate Portal, Connect, workflows, jobs, SSO, cluster state, and logs.

Upgrade after migration

Upgrade only after migration validation passes and a fresh snapshot exists. Use the currently approved upgrade path for the customer and appliance generation.
  1. Take a snapshot of each new appliance.
  2. Apply the approved intermediate update if the runbook requires one.
  3. Validate service startup and cluster health after the intermediate update.
  4. Take another snapshot.
  5. Upgrade to the approved target RapidIdentity release.
  6. Take a final post-upgrade snapshot after validation is complete.
